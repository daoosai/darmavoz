# Возвраты ЮKassa

Контур: develop / test.darmavoz.ru. Рабочие файлы: app/services/refunds.py,
payments.py, commerce_worker.py, app/api/payments.py, app/models/commerce.py,
alembic/versions/refunds_durable_queue.py, frontend/src/FinanceScreen.tsx.

## Автоматический возврат

Клиентская отмена до driver_accepted/heading_to_pickup блокирует Order FOR UPDATE,
фиксирует auto_refund_requested на существующих Payment с блокировкой FOR UPDATE
и создаёт Refund(status=queued) в той же транзакции. Даже при выключенной
интеграции или недоступной ЮKassa отмена завершается без сетевых вызовов.
Ошибка записи в БД откатывает и отмену, и очередь. Повтор клиентской отмены безопасен.

При ожидающем платеже сохраняется обязательство: payment.succeeded, polling или
фоновая сверка создают возврат поздней оплаты. waiting_for_capture отменяется
отдельной операцией /payments/{id}/cancel со стабильным ключом; Refund для
незахваченных средств не создаётся. Уже отменённые до миграции заказы автоматически
не возвращаются: их разбирают в финансовом модуле.

Архивация логистом/администратором через DELETE /admin/orders/{id} или
/logist/orders/{id} также создаёт обязательство до той же границы выезда.
Архивация после выезда не инициирует автоматический возврат: решение по сумме
принимается вручную в финансах. Статусы отмены и финансовые статусы независимы.

## Очередь и защита от повтора

Refund хранит точное тело запроса, отдельный Idempotence-Key, request_id клиента,
origin, initiated_by, причину, попытки, время первой попытки и следующей обработки.
commerce_worker выбирает до 20 наступивших задач независимо от polling платежей.
Порядок блокировок: Order → Payment → Refund. Все изменения баланса проходят
под этими блокировками. Частичный уникальный индекс разрешает несколько успешных
возвратов, но только одну незавершённую операцию на платёж.

Перед первым POST воркер сверяет платёж защищённым GET. Тело/ключ и первая попытка
сохраняются до POST. Сетевые ошибки/HTTP 5xx дают unknown и повтор с тем же телом
и ключом; backoff до часа. GET известного возврата при ошибке никогда не
освобождает резерв. После 23 часов неопределённый POST без provider_id блокируется
в manual_review: автоматический новый ключ запрещён. Срок гарантии идемпотентности
ЮKassa — 24 часа. Источники:
https://yookassa.ru/developers/using-api/interaction-format
https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds

HTTP 400 при создании — failed и needs_review; отмена заказа сохраняется.
Автоматически новые попытки с новым ключом после окончательного отказа не создаются.
Логист после устранения причины может явно создать новую операцию. manual_review
и неизвестный результат резервируют сумму до подтверждённой сверки; снимать
такой резерв произвольной кнопкой запрещено.

## Суммы и API

Payment.status остаётся succeeded. refunded_amount — сумма успешных Refund;
reserved_refund_amount — queued/creating/unknown/pending/manual_review;
refundable_amount — максимум(0, оплачено − возвращено − зарезервировано).
Агрегат refund_status: queued/creating/unknown/pending/manual_review/partial/succeeded,
либо failed/canceled при отсутствии успешной части. Все деньги Decimal, два знака.

POST /api/v1/payments/{id}/refund доступен admin и logist:
```json
{"amount":"30.00","reason":"Возврат части доставки","request_id":"<UUID>"}
```
Без amount возвращается весь доступный остаток. reason обязательно >=3 символов,
request_id обязательно. HTTP 202 означает принятие операции в устойчивую очередь,
а не факт получения денег покупателем. Повтор того же request_id возвращает
ту же операцию; изменение параметров с тем же ключом — 409. Превышение остатка,
незавершённая операция или расхождение сверки — 409. Частичный возврат и остаток
должны быть >=1 ₽. Провайдер дополнительно проверяет возможность частичного
возврата для конкретного способа оплаты.

GET /payments/{id}, /orders/{id}/payments и /finance/payments содержат три суммы.
Детали содержат историю, origin, инициатора, attempts, last_error. FinanceScreen
показывает суммы/историю, ввод суммы и причины, подтверждение и корректный текст
«Возврат поставлен в очередь». Ключ сохраняется при повторе после сетевого сбоя.
Клиент видит обработку возврата и возвращённую сумму в OrderPaymentsPanel.

Чек возврата распределяется в копейках между оставшимися исходными позициями:
сумма позиций строго равна возврату, накопленные возвраты не превышают исходные
позиции. VAT/subject/mode сохраняются; после успешного чека зачёта используется
full_payment. Если частичный возврат был до завершения заказа, чек зачёта формируется только на невозвращённый остаток. Неопределённый чек зачёта блокирует создание возврата до сверки. Внешний частичный возврат без раскладки чека блокирует дальнейшую
автоматическую раскладку до бухгалтерской проверки.

## Webhook и сверка

refund.succeeded проверяется авторизованным GET /refunds/{id}; тело webhook не
считается достоверным. Проверяются payment_id, provider_id, RUB, сумма и статус;
дополнительно проверяется объект платежа (shop/test/metadata/сумма). Уникальный
provider_id и переход состояния исключают повторный учёт и повтор события.
Поддерживаются частичные внешние возвраты из кабинета ЮKassa. Неизвестный
локальный POST сопоставляется только повтором его сохранённого ключа, а не
произвольным подбором pending-операции. Ошибка API даёт 503 для повторной доставки.
Локальные операции дополнительно сверяются воркером без зависимости от webhook.

Остаток после ручного частичного возврата при уже принятой отмене автоматически
ставится в следующую задачу после завершения текущей операции.

## Сохранение финансовой истории

Hard Delete запрещён при любой Payment, включая failed/canceled/pending и
полностью возвращённые платежи. Проверка под блокировкой Order происходит до
удаления каких-либо связанных записей. Расчёт цены PaymentQuote без Payment
не считается финансовой транзакцией. В реестре финансовые заказы имеют «В архив»,
а DELETE /admin/orders/{id}/hard возвращает 409 с понятным объяснением.
Никаких удалений Payment, Refund и их истории из hard-delete сервиса больше нет.

## Проверки и границы

tests/test_refunds.py: изолированная PostgreSQL, настоящий Alembic upgrade head,
mock API ЮKassa, отмена/offline/поздний платёж, rollback, частичные суммы/чеки,
повторы/таймаут/вебхуки, параллельные запросы и воркеры, waiting_for_capture,
окно идемпотентности, RBAC и отказ провайдера. tests/test_admin_order_hard_delete.py:
защита финансовых заказов и удаление только нефинансовых графов.
frontend/tests/e2e/refunds.spec.ts: admin/logist, mobile/desktop, повтор после
сетевого сбоя с тем же request_id, очередь и доступный остаток.

Реальный sandbox-возврат, доставка refund.succeeded из кабинета и фискальный чек
требуют отдельного QA-прогона с тестовым платежом. Нельзя считать их проверенными
по mock-тестам. Production, .env и номера сборок этой задачей не изменяются.

В финансовой таблице кнопка номера заказа останавливает всплытие click: детали загружаются один раз, поздний повторный ответ не закрывает открытую форму возврата. E2E проверяет этот путь на обеих ширинах.

Релиз всех изменений в production по явному поручению владельца: [3.1.7 (387)](../2026-10-15-emergency-release-3.1.7.md). Проверка sandbox/webhook/фискальных чеков остаётся отдельным QA-проходом; существующие отмены автоматически не возвращаются.
