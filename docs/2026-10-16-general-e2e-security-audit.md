# Дармавоз — E2E-аудит, Bug Hunting и проверка безопасности

Дата: **16 октября 2026, UTC**. Контур: **https://test.darmavoz.ru/app**, нода foptyvllka.
Исходники: /opt/darmavoz_test, ветка develop, HEAD **e58697c1**.
Runtime: /opt/darmavoz_test_deploy, **6574b63399359d46d5d38b8476c88faf04a24390**.
Разница исходников и runtime — следующий документационный коммит. Версия в веб-интерфейсе: 3.1.7.

**Результат: 10 замечаний — 2 критических риска, 5 средних, 3 минорных.** Критический приоритет относится к известной уязвимости мобильной зависимости и внешней доступности инфраструктуры. Захват аккаунта, кража денег или утечка БД в этой проверке не воспроизводились. Считать приложение готовым к боевым платежам только на основании пройденных пользовательских сценариев нельзя.

Код приложения, миграции, .env и версии не менялись. Деплоя, коммита и push нет: задача только на анализ. Production и реальные платежи не использовались.

## Как проверяли и что означает результат

- Playwright Chromium выполнялся **на ноде Дармавоза**, по опубликованному тестовому сайту, без подмены API.
- Открыты кабинеты client, driver, supplier, equipment_owner, water_septic_partner, logist, admin, manager. Для проверки чужих данных использован второй клиент.
- Для изоляции созданы собственные QA-профили; основная навигация проверялась с временными JWT, выпущенными штатной серверной функцией. Это **не проверка полного входа и регистрации каждой роли**. Отдельно проверен настоящий password login собственного QA-admin; у водителя — публичная форма регистрации.
- Собраны console/pageerror, HTTP 4xx/5xx, DOM-текст, измерения переполнения и скриншоты. Матрица RBAC: 9 типов доступа × 10 GET-endpoints = 90 запросов, дополнительно адресные операции.
- Основной обход: 40 состояний страниц. Дополнительно выполнены checkout, формы, карта, смена, модерация, удаление и проверки вёрстки. Мобильный viewport 390 px; целевые проверки 320/390/768/1440 px.
- Проведены npm audit для lockfile и pip-audit **списка установленных пакетов backend_test**, в отдельном одноразовом контейнере без настроек приложения.
- Доступность служебных портов проверена с хоста агента, вне ноды Дармавоза. Нагрузочные, разрушающие и массовые атаки не выполнялись.
- Отсутствие ошибок в проверенных сценариях не доказывает отсутствие всех уязвимостей.

## 🔴 Критические (блокирующий приоритет)

### SEC-01. В мобильных зависимостях зафиксирован уязвимый Capacitor 8.4.2

**Тип доказательства:** установленная/зафиксированная версия + официальный security advisory; эксплуатация на устройстве не проверялась.

**Факт:** frontend/package-lock.json фиксирует @capacitor/android, @capacitor/ios и @capacitor/core **8.4.2**. npm audit помечает Android/iOS как critical по **GHSA-rvm3-566m-v7fv / CVE-2026-103922**.

По [бюллетеню разработчика Capacitor](https://github.com/ionic-team/capacitor/security/advisories/GHSA-rvm3-566m-v7fv), уязвимый внутренний HTTP proxy позволяет загрузить внешний документ с доверием origin приложения. При активации подходящей ссылки внутри WebView возможен доступ к localStorage и доступным нативным плагинам. Отключение CapacitorHttp само по себе не устраняет проблему. В ветке 8.4 исправление указано в **8.4.3**.

**Воспроизведение проверки:** посмотреть версии lockfile; выполнить npm audit --json; сопоставить диапазон с advisory.

**Влияние:** потенциальная компрометация сессии/возможностей мобильного приложения при наличии пути доставки вредоносной ссылки.

**Ограничение:** конкретный APK/AAB, размещённый в Google Play, не выгружался и не исследовался; совпадение его зависимостей с develop пока не доказано. Сквозная доставка ссылки и её исполнение в native WebView не проверены.

**Критерий закрытия:** подтвердить состав опубликованного приложения, обновить затронутые пакеты до проверенной исправленной совместимой версии, пересобрать native-приложение и проверить на устройстве. Одного веб-деплоя недостаточно.

**Доказательства:** reports/2026-10-16-general-audit/npm-audit.json.

### SEC-02. Тестовая инфраструктура доступна через публичные служебные порты

**Тип доказательства:** подтверждённая внешняя сетевая доступность; обход аутентификации не обнаружен.

С внешнего хоста установлено TCP-соединение с нодой на портах:

| Порт | Сервис | Наблюдение |
|---|---|---|
| 5433 | PostgreSQL test | TCP доступен |
| 6380 | Redis test | TCP доступен; PING без пароля вернул NOAUTH |
| 8001 | backend_test | HTTP /health → 200, напрямую через uvicorn |
| 9002 | MinIO test API | TCP доступен; корень без авторизации → 403 |
| 9003 | MinIO test console | HTTP → 200 |

docker-compose.test.yml публикует эти порты без ограничения loopback. ss на ноде подтверждает 0.0.0.0.

**Ожидается:** БД/Redis и административные интерфейсы доступны из доверенной сети; внешний API проходит через настроенный HTTPS reverse proxy.

**Влияние:** инфраструктура доступна для атак извне, прямой HTTP backend обходит внешнюю HTTPS-точку входа. Это не утверждение о доступе к данным без пароля. Сценарии с реальными production-сервисами не проверялись.

**Критерий закрытия:** ограничить публикацию/доступ, проверить Docker firewall и повторить внешнюю проверку. Сохранить необходимый внутренний доступ сервисов.

**Доказательства:** external-security.json; docker-compose.test.yml, вывод ss.

## 🟡 Средние (логика, API, безопасность)

### BUG-01. Водитель может создавать оптовые заявки через API

**Роль:** approved driver с approved vehicle.

1. Войти водителем; открыть «Опт»: доступны «Все» и «Избранное», кнопки создания нет.
2. Отправить POST /api/v1/wholesale-requests?draft=true с валидными полями WholesaleInput.
3. Сервер возвращает **201**, создаёт draft с author_id водителя.

**Ожидается:** создание разрешено поставщику; driver получает 403 независимо от интерфейса.

**Факт:** board_user допускает водителя для просмотра, а create использует ту же зависимость без отдельного ограничения автора. Подтверждена запись черновика; отправка водительского черновика на модерацию отдельно не запускалась.

**Влияние:** обход разграничения функций ролей. Это класс [OWASP API5 — Broken Function Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/).

**Доказательства:** api.json, wholesale-create/driver → 201; app/api/wholesale.py, create.
**Критерий закрытия:** серверное ограничение всех операций публикации/редактирования согласно матрице ролей, сохранение read-only ленты водителя.

### SEC-03. На password login не наблюдается ограничение неверных попыток

1. Для собственного QA-admin выполнить 12 последовательных POST /api/v1/auth/login с неверным паролем.
2. Все ответы — **401**; 429/временная блокировка не появились.
3. Сразу после этого правильный пароль даёт **200** и admin JWT.

В просмотренном обработчике login отсутствует счётчик/лимитер неверного пароля. Ограничения SMS/OTP не защищают этот этап.

**Ожидается:** серверная защита от подбора пароля с контролем аккаунта и источника.
**Влияние:** облегчение подбора паролей сотрудников; захват аккаунта не воспроизводился.
**Ограничение:** 12 запросов не доказывают отсутствие любого возможного внешнего порога; установлено отсутствие защиты в исследованном обработчике и в проверенном диапазоне.
**Доказательства:** final-api.json, password-throttle, real-password-login-admin.
**Критерий закрытия:** зафиксировать политику ограничения, проверить её через опубликованный endpoint и прямой backend.

### SEC-04. В backend и цепочке сборки есть зависимости с опубликованными уязвимостями

- В работающем backend: **starlette 0.36.3**, **python-jose 3.3.0**.
- pip-audit сообщает, в частности, advisories Starlette для обработки multipart (CVE-2024-47874, CVE-2025-54121) и python-jose (CVE-2024-33663/33664).
- npm audit: **19 затронутых пакетов**: 4 critical, 9 high, 6 moderate. Это число пакетов, а не независимых эксплуатационных цепочек. Capacitor выделен в SEC-01; оставшиеся critical включают proxy-addr и tar.
- Найдены также предупреждения для build/runtime tooling, например pip/setuptools. Они требуют иной оценки, чем уязвимости публичного API.

**Ожидается:** оценённая и обновлённая цепочка зависимостей перед финансовым запуском.
**Влияние:** потенциальные DoS и другие риски при выполнении условий соответствующих advisories.
**Ограничение:** DoS не запускался; применимость каждой записи к конкретному коду не доказана. Например, JWE и асимметричные JWT-сценарии нельзя автоматически считать доступными только из-за установленного python-jose. Дубликаты aliases в pip-audit не следует считать отдельными багами.
**Доказательства:** python-audit.json, npm-audit.json.
**Критерий закрытия:** составить адресный план обновлений и проверки достижимости уязвимых функций; не выполнять слепой audit fix --force.

### BUG-02. Допустимое длинное название точки вызывает HTTP 500

**Роль:** supplier с нормальным телефонным логином.

1. POST /api/v1/supplier/points: name = «QA AUDIT » + 130 букв «А»; short_name не передавать; остальные поля корректны.
2. Получить **500** вместо создания/валидационной ошибки.
3. Лог PostgreSQL: StringDataRightTruncationError, character varying(100).

**Причина:** схема разрешает name до 255 символов; create_supplier_point подставляет name в short_name, а short_name ограничен 100. В форме названия нет maxLength.

**Ожидается:** корректное сохранение короткого имени либо понятный 422 до обращения к БД.
**Влияние:** поставщик не может сохранить валидную по схеме анкету; сервер показывает общую внутреннюю ошибку.
**Доказательства:** recheck.json, long-point-name; app/api/supplier_points.py, app/schemas/quarry.py; диагностические логи.
**Критерий закрытия:** согласовать ограничения UI/schema/БД и проверить имя на границах 100/101/255 символов.

### BUG-03. Строковые координаты дают HTTP 500 вместо валидационного ответа

1. POST /api/v1/supplier/points с lat: "57.152", lon: "65.54".
2. Получить **500**.
3. Сервер: TypeError — сравнение str с int в QuarryBase.validate_lat.

**Ожидается:** приведение числовой строки к числу либо 422. Некорректный тип пользовательского поля не должен превращаться в исключение сервера.
**Влияние:** дефект API-валидации; штатная браузерная форма с числовыми координатами его не воспроизвела.
**Доказательства:** recheck.json, string-coordinates; app/schemas/quarry.py.
**Критерий закрытия:** безопасная нормализация типов и одинаковое поведение lat/lon на create/update.

**Ожидается:** ширина документа не превышает viewport; select сжимается внутри контейнера.

## Как трактовались ошибки и ограничения

- 401/403/404 в негативных проверках доступа — ожидаемые ответы, не баги.
- 422 для невалидного UUID города и 409 для недоступного города — ожидаемая валидация.
- Некорректные не-UUID ключи идемпотентности в первых пробах дали 400. С UUID проверка прошла; в баги это не включено.
- Предварительные locator timeout в скриптах перепроверены. Они возникали из-за неточных селекторов/открытой предыдущей модалки; не выдаются за зависшие экраны приложения.
- Первые попытки создать точку под искусственным длинным QA-логином вызвали 500 из-за подстановки username в телефон. После замены только собственных QA-логинов на нормальные телефоны обычное создание прошло. Этот артефакт подготовки профиля **не включён** в список продуктовых багов.
- Service Worker registration blocked by Playwright и предупреждения GPU/WebGL относятся к условиям запуска; исключений приложения на обычном обходе нет. Основной прогон блокировал service worker, поэтому офлайн-режим/устаревший SW-кэш не проверены.
- На /app отсутствуют CSP/HSTS/X-Content-Type-Options/X-Frame-Options/Referrer-Policy в проверенном ответе. Это отдельное наблюдение по усилению HTTP-конфигурации, без доказанной эксплуатационной цепочки и без включения в 10 замечаний.
- Не проводились: эксплуатация native WebView, проверка опубликованного Play APK, полный цикл регистрации/входа каждой роли, реальная SMS/email-доставка, загрузка всех типов файлов, физические push/GPS/background permissions, реальные оплаты/чеки/возвраты, нагрузочный тест, исчерпывающий pentest всех API.
- Примеры UI проверялись с текущими тестовыми данными; массовая модерация существующих пользовательских объектов не выполнялась.
- Вывод о готовности production делать нельзя: исследован test/develop, а не опубликованный production build.

Скрипты требуют временный приватный файл авторизации /tmp/darmavoz-audit-auth.json. После завершения он удаляется, сессии QA аннулируются. Для повторения требуется создать новые изолированные QA-профили; не использовать production или чужие платежи.

## Рекомендуемая очередность последующей работы

1. Проверить опубликованный native-артефакт и закрыть SEC-01; ограничить внешние служебные порты SEC-02.
2. Закрыть API-обход ролей и защиту password login; разобрать достижимость уязвимостей backend/dependencies.
3. Исправить обе ошибки 500 поставщика и мобильный фильтр городов.
4. Согласовать шаблоны отказа и улучшить доступность кнопок.
5. После исправлений повторить соответствующие сценарии; отдельно провести нативный тест и финансовый sandbox-цикл с webhook/возвратом/чеками.
