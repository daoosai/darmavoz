# Спринт 24 — оптовые заявки, ЮKassa и финансы

Версия приложения: 3.2.0, Android/iOS build 317.

## Где открыть

- Партнёры (только водитель и поставщик): вкладка «Опт» в основной нижней навигации на mobile и desktop. Все активные водители и поставщики имеют доступ без отдельного допуска. Дополнительный пункт Профиль → Оптовые заявки остаётся для активных водителей и поставщиков. У спецтехники, воды/септиков и B2C-клиентов перехода нет.
- Администратор: Профиль → Оптовые заявки → Проверка.
- Администратор и логист: Профиль → Финансы.
- Клиент: Заказы → Оплата заказа.
- Сотрудники: карточка заказа → Подтвердить стоимость для оплаты.

Оптовые объявления самостоятельны: согласование перевозки происходит по телефону.
Встроенные платежи относятся к обычным заказам. Доступ к оптовой ленте не выдаётся клиентам.

## Настройки ЮKassa

Секреты вводит владелец проекта в существующий серверный `.env`. Кодекс их не меняет.
Backend получает `.env` через существующий `env_file` Docker Compose; новую конфигурацию
необходимо применить пересозданием только `backend_test` после внесения ключей.

До одобрения магазина достаточно оставить `PAYMENTS_ENABLED=false`: приложение и worker работают без ключей.
Для подключения нужны следующие параметры:

```dotenv
PAYMENTS_ENABLED=false
YOOKASSA_SHOP_ID=
YOOKASSA_SECRET_KEY=
YOOKASSA_API_BASE_URL=https://api.yookassa.ru/v3
# Здесь указать полный HTTPS адрес приложения своего контура, например https://<тестовый-домен>/app
PAYMENT_RETURN_URL=
PAYMENT_TEST_MODE=true
PAYMENT_REPORT_TIMEZONE=Asia/Irkutsk
PAYMENT_POLL_INTERVAL_SECONDS=60
PAYMENT_RECEIPTS_ENABLED=false
# Код НДС и система налогообложения утверждаются владельцем / бухгалтерией.
# PAYMENT_RECEIPT_VAT_CODE=<утверждённый код НДС>
# PAYMENT_RECEIPT_TAX_SYSTEM_CODE=<утверждённый код системы налогообложения>
PAYMENT_RECEIPT_MODE=full_prepayment
```

Для необязательных числовых значений удалить строку до настройки, а не оставлять пустое значение.
Для тестов использовать тестовый магазин и `PAYMENT_TEST_MODE=true`.
Для реальных платежей установить `PAYMENT_TEST_MODE=false`, подключить «Чеки от ЮKassa»,
заполнить утверждённые параметры чеков, поставить `PAYMENT_RECEIPTS_ENABLED=true` и
только затем `PAYMENTS_ENABLED=true`. Backend запрещает реальные платежи без настройки чеков.
При предоплате (`full_prepayment`) после перехода заказа в `completed` worker отправляет чек зачёта;
для оплаты после оказания услуги используется утверждённое значение `full_payment`.
Покупатель указывает электронную почту для чека. Сумма позиций материала и доставки совпадает с оплатой.

В кабинете ЮKassa настроить адрес уведомлений:
`https://<домен-контура>/api/v1/webhooks/yookassa`.
События: `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
Уведомление не является подтверждением оплаты само по себе: backend сверяет объект через API ЮKassa.
Сумма, валюта, магазин, признак тестового платежа и идентификаторы заказа должны совпасть.

## Финансовые правила

- Логист подтверждает сумму материала и доставки. Подтверждение сохраняется отдельной версией.
- Изменение цен/состава до оплаты отменяет прежнее подтверждение суммы.
- Активная, неопределённая или успешная платёжная попытка блокирует изменение стоимости.
- Один заказ имеет максимум одну активную либо успешную оплату; повторное нажатие использует прежнюю попытку.
- При таймауте исходный запрос повторяется с тем же ключом; после 23 часов неизвестный запрос
  без идентификатора провайдера требует ручной сверки. Новое списание не создаётся.
- Исполнение заказа сохраняет существующую логику и не блокируется статусом оплаты.
- Отмена заказа не делает автоматический возврат. У оплаченного отменённого заказа показывается требование проверки.
- Администратор инициирует полный возврат с причиной. Логист имеет доступ только к просмотру и экспорту финансов.
- Архивирование заказа не удаляет платежи. Миграция не переносит существующие заказы в «оплаченные».
- Отчёты считают оплату по дате успешного платежа и возврат по дате успешного возврата в настроенной часовой зоне.
- Реестр фильтруется по дате создания либо оплаты, статусу, способу и заказу; выгрузка CSV повторяет его фильтры.
- Финансовые суммы в новых API передаются десятичными строками; существующие суммы OrderOut сохраняют числовой контракт.

Частичные оплаты, частичные возвраты, комиссии, банковские выписки, выплаты перевозчикам и
оплата оптовых договорённостей не входят в этот спринт. Возвраты предпочтительно инициировать из приложения,
чтобы сохранить причину и автора. Полный возврат из кабинета ЮKassa импортируется по проверенному уведомлению;
расхождение с суммой возврата провайдера отмечается для ручной проверки.

## Проверка и развёртывание

```text
python -m pytest -q tests/test_sprint24.py
python -m pytest -q tests/test_sprint24_api.py
npm run lint
npm run build
npx playwright test tests/e2e/sprint24.spec.ts
```

API-тесты используют отдельную временную PostgreSQL БД и удаляют только её.
Тестовые карты и ответы провайдера проверяются отдельно после выдачи тестовых ключей ЮKassa.
Без ключей проходят проверки отказа оплаты, API-контрактов и имитация платёжных сценариев.

CI/CD ветки `develop` выполняет backend/frontend проверки, `alembic upgrade head`, пересоздание
и перезапуск `backend_test`, healthcheck и проверку новых маршрутов OpenAPI.
Android/iOS workflows синхронизируют официальный плагин Browser через `cap sync`.
Native возврат использует зарегистрированную схему `darmavoz://payment?payment_order=<uuid>`;
страница HTTPS возврата предлагает открыть приложение, приложение перечитывает статус с backend.
