# PROJECT STATE — Дармавоз

## 1. Описание проекта

Дармавоз.рф — маркетплейс доставки сыпучих материалов и спецтехники. По своей логике это сервис уровня «Яндекс.Такси для самосвалов»: клиент выбирает материал, объем и адрес доставки, система подбирает подходящие точки забора, рассчитывает стоимость, а дальше заказ проходит через логистику, водителя и поставщика.

Ключевые направления системы:

- доставка нерудных и строительных материалов;
- выбор точки забора: карьер, накопитель, склад, поставщик;
- расчет цены с учетом материала, расстояния и типа машины;
- диспетчеризация заказов между клиентом, логистом и водителем;
- мобильный и web-доступ для клиентского сценария.

## 2. Роли в системе

### Client

Клиент оформляет заказ на материал, выбирает объем, адрес доставки, получает расчет стоимости, отслеживает статус заказа и взаимодействует с корзиной и картой точек.

### Driver

Водитель принимает заказы, видит точку погрузки, маршрут, статус заказа и проходит операционные этапы исполнения доставки.

### Admin / Logist

Администратор и логист управляют каталогом, машинами, точками забора, модерацией заявок, ценами, заказами и логистической цепочкой исполнения.

### Supplier

Поставщик подает заявки на размещение точек забора, управляет своими точками и материалами в рамках поставщицкого кабинета.

## 4. Ключевые бизнес-модели

### Order

`Order` — центральная сущность клиентского заказа.

Основные свойства по текущей модели:

- связь с клиентом (`client_id`);
- связь с водителем (`driver_id`);
- связь с выбранной машиной (`delivery_option_id`);
- связь с точкой забора (`quarry_id`);
- адреса и координаты погрузки и доставки;
- километраж, стоимость доставки, итоговая сумма;
- статус заказа;
- soft delete через флаг `is_deleted`.

Soft delete реализован без физического удаления записи: заказ помечается как удаленный, а связанные активные офферы отменяются.

Точка забора уже встроена в модель заказа через `quarry_id`, а также снапшотные поля `pickup_address`, `pickup_lat`, `pickup_lon`.

### DeliveryOption

`DeliveryOption` описывает тип машины и тариф доставки.

В актуальной модели есть:

- `title`;
- `capacity_m3`;
- `base_price`;
- `delivery_rate_per_km`;
- `min_price_quarry` — минимальная стоимость доставки от карьера;
- `min_price_warehouse` — минимальная стоимость доставки от накопителя/склада;
- `image_url`;
- `is_active`, `sort_order`.

Это уже отражает новую экономическую модель с двойной минималкой в зависимости от типа точки забора.

### Quarry

`Quarry` в системе — это универсальная точка забора материала.

Модель покрывает:

- карьер;
- накопитель;
- склад;
- поставщик.

Основные поля:

- `name`, `short_name`;
- `point_type`;
- `address`, `description`;
- `lat`, `lon`;
- `min_delivery_price`;
- `rating`;
- `owner_user_id`;
- `moderation_status`;
- `moderation_comment`;
- `is_active`.

Точка связана с:

- материалами;
- машинами (`delivery_options`);
- фотографиями (`media_files`);
- владельцем;
- заказами.

Модерация встроена в доменную модель и поддерживает жизненный цикл точки до публикации.

## 5. Стейт-машина заказа

Текущая цепочка статусов в коде включает следующие состояния:

1. `draft`
2. `created`
3. `searching_driver`
4. `offered_to_driver`
5. `driver_assigned`
6. `driver_accepted`
7. `heading_to_pickup`
8. `arrived_at_pickup`
9. `loading`
10. `heading_to_client`
11. `delivered`
12. `completed`

Терминальные и служебные статусы:

- `cancelled`
- `timeout`
- `no_driver_found`

Практический основной маршрут исполнения сейчас выглядит так:

`created -> searching_driver -> offered_to_driver -> driver_assigned -> driver_accepted -> heading_to_pickup -> arrived_at_pickup -> loading -> heading_to_client -> delivered -> completed`

Альтернативная ветка завершения:

- отмена заказа: `cancelled`;
- не найден водитель: `no_driver_found`;
- таймаут бизнес-процесса: `timeout`.

## 6. Архитектура CI/CD и контуры

Проект работает в двухконтурной схеме.

### Test contour

- рабочая ветка: `develop`
- домен: `test.darmavoz.ru`
- исходники на сервере: `/opt/darmavoz_test`
- runtime-контур Docker: `/opt/darmavoz_test_deploy`

GitHub Actions по `develop`:

- обновляет test-исходники на сервере;
- деплоит frontend в тестовый контур;
- выполняет backend-миграции Alembic;
- перезапускает test-контейнеры;
- собирает Android APK для тестовой среды (`darmavoz-test.apk`).

### Production contour

- рабочая ветка: `main`
- домен: `darmavoz.ru`
- исходники на сервере: `/opt/darmavoz`
- runtime-контур Docker: `/opt/darmavoz_deploy`

GitHub Actions по `main`:

- обновляет production-исходники;
- деплоит production frontend;
- выполняет Alembic-миграции;
- перезапускает production backend.

### Важное замечание по APK

Целевая архитектура предполагает связку:

- `develop` -> test.darmavoz.ru + test APK
- `main` -> darmavoz.ru + production APK

Однако по текущему состоянию workflow сборки production APK привязан не к `main`, а к отдельной ветке `feature/sprint-12`. Это техническое расхождение между целевой схемой и фактической настройкой CI, которое стоит учитывать в следующей сессии.

## 7. Итоговое текущее состояние

На текущем этапе Дармавоз — это fullstack-система для расчета, оформления и исполнения заказов на доставку материалов с опорой на:

- клиентскую корзину и расчет;
- карту и каталог точек забора;
- модерацию точек;
- роли поставщика, логиста и водителя;
- backend-диспетчеризацию заказа;
- web и Android delivery-поток через единый API.

Файл создан как актуальный паспорт проекта для быстрой синхронизации новой сессии разработки.
